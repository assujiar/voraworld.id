# VORA technical architecture

## Shape

One **Next.js 15 App Router** application (React 19, TypeScript strict) deployed as Vercel serverless functions in front of **Supabase PostgreSQL and Storage**. There is no separate API service: pages are React Server Components, forms post to **Server Actions**, and the few non-page endpoints (PDFs, uploaded files, sitemap, robots, the cron dispatcher) are route handlers.

```
 browser ──► middleware (admin gate: signed cookie) ──► Server Component / Route Handler / Server Action
                                                           │
                              src/server/*  (domain code)  ├──► PostgreSQL  (postgres.js, SQL in code, schema from migrations/)
                                                           ├──► Supabase Storage (REST, server-side secret key)
                                                           └──► SMTP (nodemailer, via the email outbox)
```

* **Rendering.** Public pages, admin pages and document pages are rendered on the server on every request (`dynamic = 'force-dynamic'`), because their content comes from the database. Crawlers therefore receive complete HTML, not an empty client shell. Browser JavaScript is limited to small client components (form state, the invoice and quotation line editor, the rich-text editor, the mobile menu and the motion script).
* **Languages.** `/en/...` and `/id/...` are explicit routes; `/` redirects to `/en`. English is the default; the Indonesian copy lives in `src/content/`. Articles and CMS pages each carry one language.
* **Persistence.** `postgres` (porsager) with `prepare: false` (required behind Supabase's transaction pooler), one connection per serverless instance on Vercel (`DB_POOL_MAX`, default 10, elsewhere), camelCase property names mapped to snake_case columns, and `bigint` returned as JS numbers. Money columns are `bigint` (migration `0016`), so amounts above IDR 2.1 billion are safe. SQL is written in the code; the only way the schema changes is a numbered file in `migrations/`. `src/server/schema.ts` is generated from the migrated database and a test fails if it drifts.
* **Time.** A document's "today" is the date in `Asia/Jakarta` (`src/server/dates.ts`), not in UTC.

## Authentication and authorization

* **Credentials and sessions.** Supabase Auth owns passwords, sessions, refresh, sign-out and password reset (`@supabase/ssr`, cookies `HttpOnly`, `SameSite=Lax`, `Secure` in production, 8 hours). The application keeps no password hash and no session secret. Accounts are created by an administrator in the Supabase dashboard; there is no registration.
* **Who may use the portal.** `public.users` (id, email, role, active, `auth_user_id`) is the membership table. A person signs in only if a Supabase Auth account exists AND an active row here links to it with role `admin`; the role is never read from user metadata. The middleware refreshes the session and refuses visitors with none; every page, route handler and Server Action asks Supabase Auth (`getUser()`) and checks the row again, so a deactivated account or an ended session stops working at once. `promote_admin()` / `deactivate_admin()` (migration 0023) manage membership from the SQL Editor.
* **Sign-in protection.** Failed attempts are recorded in `login_attempts`: five per email or thirty per IP address within 15 minutes lock further attempts out (even with the right password). Unknown accounts cost the same time as wrong passwords (a dummy hash is always verified), and the error message is the same.
* **One role.** The portal has a single role, `admin`, which can open every menu. Any other role value in `users.role` has **no access at all**; migration `0017` converts old `superadmin` accounts to `admin` and nothing else. Consequence: there is no separation of duties inside the system (see `ADMIN_SETUP_GUIDE.md` §2).
* **Two checks, on purpose.** `src/middleware.ts` answers anonymous requests to `/admin/**` from the signed cookie alone (redirect to sign-in for pages, 401 for other methods, 403 for a non-admin role), before any page code runs. Pages, route handlers and Server Actions then repeat the authoritative check against the database (account active, credential unchanged, admin role).
* **Every Server Action is a public HTTP endpoint**, so the guard cannot be optional: each exported action in `src/actions/*.ts` must be `return adminRun(form, fn)` / `adminRunForm` (signed-in forms) or `publicRun` (the five visitor actions: sign-in, sign-out, contact, quote request, quotation approval upload). `adminRun` checks, in order: same origin, signed in (else redirect to `/admin/login`), admin role (403), then runs the handler. `tests/action-guards.test.ts` reads the source of every action and also *executes* every admin action as an anonymous visitor, as accounts with other roles, as a deactivated or stale session, with a forged cookie and from another origin, and proves that nothing in any table changed.
* **CSRF.** Next.js verifies the `Origin` of every Server Action call; `assertSameOrigin` repeats it in our own wrapper. Cookies are `SameSite=Lax`. Sign-out is a POST. Public forms carry a hidden honeypot field and a database-backed throttle (four submissions per email address per 15 minutes) that holds across serverless instances. Put a WAF or bot protection in front of the public forms in production.
* **Browser protections.** Every response carries a Content-Security-Policy with no third-party origins (images may come from `*.supabase.co`), `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff`, a strict referrer policy, `Permissions-Policy`, and HSTS in production. Admin responses are `noindex` and `no-store`; verification and approval pages are `noindex`, `no-store` and send no referrer. The CSP still allows inline scripts and styles because Next.js needs them (see `KNOWN_LIMITATIONS.md`).

## CMS

`articles` (HTML sanitized on the server by an allow-list: no scripts, no inline styles, https/mailto/same-site links only), `pages` and `sections` (a draft that is previewed and then published as a JSON snapshot, which is what visitors see), `revisions` (an article stores its previous state at every save, a page stores the previously published snapshot at every publish; restoring one is itself recorded), `settings` (company details and policies), `navigation_items`, `faqs`, `coverage` (a region appears on the public Network page only while it is marked active, and the time it was marked is recorded), `seo_redirects` (301 with relative-path validation), `media` (metadata only; the bytes are in Storage). Uploaded images are identified by their bytes (PNG, JPEG, WebP, AVIF, structurally checked), never by file name or browser-supplied type.

## Finance

* **Customers, bank accounts, quotations, invoices, payments, receipts**, all in SQL, all amounts as integer minor units. Calculations use exact BigInt decimal arithmetic with half-up rounding (`src/server/money.ts`); the browser never supplies a total.
* **Numbering.** `INV|RCP|QUO-VORA-<OWNER_CODE>-<YYYYMM>-<RANDOM_5>` with a random five-digit tail, a transaction-scoped advisory lock per (kind, owner, month) and a unique index as the final guard. See `NUMBERING_POLICY.md`.
* **Payments.** A payment claim is stored as `pending_confirmation` and changes nothing else. Open claims reserve balance so the invoice cannot be over-claimed. Confirming locks the invoice, then the payment (always in that order), recomputes the invoice from confirmed payments, creates the receipt and queues the emails, all in one transaction; if several people confirm at once exactly one wins. Voiding a receipt reverses its payment; voiding an invoice cancels open claims. Bank details are snapshotted on the invoice when it is created, so later edits never alter an issued invoice.
* **E-meterai.** A receipt for a non-IDR payment or more than IDR 5,000,000 is created as `pending_stamp` and withheld. The owner applies an authentic e-meterai outside this system and uploads the stamped PDF; it is inspected (see below), stored privately with its SHA-256, and only then released. The software never calls a provider and cannot judge a stamp.
* **Verification.** Each document gets an unguessable 36-byte token; the QR on the PDF opens `/verify/<token>`, which shows only the document type, reference, issuer, date and current status. Only the token's SHA-256 is needed for lookup. Voiding revokes it.

## Documents (PDF)

`pdf-lib` draws A4 PDFs on the server with standard Courier fonts and the brand PNGs embedded from `src/server/pdf/brand-assets.ts` (generated by `npm run build:pdf-assets`). The renderers (`src/server/pdf/`) receive plain data and never touch the database. Invoices flow five items per page and add a summary page when the final block does not fit; quotations are measured onto one page (font size 8.0 down to 6.5, otherwise they fail loudly with `PdfLayoutError` instead of clipping) and switch to the paginated layout beyond ten items; receipts are one page. Issued receipts that were stamped are served from the stored, hash-checked file, never re-rendered.

**Uploaded PDFs** (stamped receipts, customer-signed quotations) are inspected before storage by `src/server/finance/pdf-inspect.ts`: the `%PDF-` header, the size limit, a structural parse (any failure is reported as an invalid or damaged PDF), a page-count window, no `OpenAction`/`AA`/JavaScript/Launch actions, and extracted text that must contain the document's reference numbers. Files are stored in the **private** bucket and every read re-checks the stored SHA-256.

## The commercial workflow (Phase 3A, migration 0026)

The customer is the commercial entity; a lead is only one possible source of business. **Path A:** lead -> customer -> quotation (`convertLead`, `lead_convert`: matches are shown, an existing customer can be linked, the lead is kept and gets `customer_id`/`converted_at`, a second conversion is refused). **Path B:** customer (entered directly) -> quotation, with `lead_id` empty throughout. A quotation always has a `customer_id` (`quote_has_recipient` still allows historical rows with only a lead). Quotation states: `draft`, `issued`, `awaiting_approval`, `customer_approved` (the customer uploaded a signed PDF), `validated` (an admin checked the signature and stamp), `rejected`, `void`; only `validated` unlocks delivery notes (`deliveries.quotation_id`) and invoices (`invoices.quotation_id`). An invoice bills one or more delivered notes through `invoice_delivery_notes`; a partial unique index (`released_at IS NULL`) makes a note billable once, `invoice_create` re-checks customer, quotation, validation, currency and the quoted total under row locks, and voiding releases the links. `sendInvoice` queues ONE email with two attachments (invoice + pre-payment receipt, `email_job_attachments`) and refuses the whole package if either is not released. Structured item tables (`ItemsTable`) post `item_<column>` values that `rowsFromForm` reads; amounts are recalculated on the server.

## Delivery notes and proof of delivery

A delivery note (surat jalan, `src/server/delivery/deliveries.ts`, migration 0025) is written and issued in the admin and prints with a QR code. The **driver or courier** scans it at the handover, on their own phone, at `/pod/<capture token>`: they confirm who they are (pre-filled from the note), the receiver gives their name and position and signs on the driver's screen, the driver photographs the goods (reduced on the phone to stay under Vercel's 4.5 MB request limit) and must have the phone's location switched on: the proof is refused without it (form, service and the `delivery_submit_proof` function all check), and the position is read again at the moment of sending (`Permissions-Policy: geolocation=(self)` is allowed on `/pod/*` only); the time is the server's. The proof can be given once (`delivery_submit_proof` locks the note); Finance can reject a wrong one, which stays as history and re-opens the same QR code. Evidence files (signature, photos) go to the private bucket **before** the database function commits and are removed if it refuses; every read re-checks their SHA-256. The consignee is emailed a second, different address (`/pod/view/<view token>`). Both tokens are 36 random bytes, stored (a printed QR must keep working), and the pages are `noindex`, `no-store`, `no-referrer`. Admin: `/admin/deliveries` (list, draft editing, issue, void, evidence, delivery-note PDF, proof PDF, resend email, reject proof).

## Storage

`src/server/storage.ts` talks to the Supabase Storage REST API with the server-side secret key (`sb_secret_…` goes in `apikey` only; the legacy JWT key also goes in `Authorization`). Buckets: `vora-media` (public: website and article images) and `vora-documents` (**private**: stamped receipts and signed quotations, only reachable through authenticated admin routes or the private approval link). In production the Supabase URL must be https. Without Supabase configuration, and only when `APP_ENV` is not `production`, files go to a local directory for development and tests.

## Email

SMTP settings are entered in the admin portal; the password is stored AES-256-GCM encrypted with `MAIL_ENCRYPTION_KEY` (32 random bytes, base64). Templates and rules are rows in SQL (seeded by migrations `0008`, `0009`, `0014`, `0018`); **every rule starts disabled**. Messages are queued in `email_jobs` with a de-duplication key, claimed atomically (`for update skip locked` with a 10-minute lease, so two workers or an admin click can never send one message twice), retried with growing back-off (2, 4, 8 and 16 minutes after the first four failures; the fifth failure marks the message `failed`, and an admin can press **Retry**), and attached PDFs are rendered at send time and refused if the document is void or still a draft, if a receipt's payment is not confirmed, or if a required e-meterai has not been uploaded. Sending starts right after the response that queued the message (`after()`), and a daily Vercel cron (`/internal/mail/dispatch`, bearer `CRON_SECRET`) retries what is left. Template values are HTML-escaped before substitution.

## Start-up and configuration

`src/instrumentation.ts` calls `assertConfig()` when the server boots, so a bad production configuration fails immediately with a readable message: the Supabase URL, publishable key and secret key must be set, and in production `PUBLIC_BASE_URL` must be https (default `https://voraworld.id`). Everything the code reads from the environment goes through `src/server/env.ts`, and a test keeps `.env.example` in sync with it. The admin dashboard shows a setup checklist built by `src/server/setup-check.ts` (presence only, never values).

## Database access

The server has no database connection string. `src/server/data` wraps supabase-js with the secret key: plain reads and writes use the Data API (PostgREST), and every operation that must be atomic is one PostgreSQL function (`migrations/0024_data_api.sql`: invoice, payment, receipt, quotation, document, CMS, lead and mail-queue functions, with row locks, advisory-locked numbering and audit rows in the same transaction). The functions run with the caller's rights (SECURITY INVOKER), have a pinned `search_path`, raise business refusals as SQLSTATE `VRnnn`, and are executable only by `service_role`; all tables are closed to the `anon` and `authenticated` roles. `npm run db:migrate` (optional, owner's computer) is the only code that opens a PostgreSQL connection.

## SEO

Server-rendered titles and descriptions per page and per locale, canonical URLs from `PUBLIC_BASE_URL`, `hreflang` pairs, Open Graph and Twitter tags, Organization JSON-LD on every public page and Service JSON-LD on service pages, a dynamic `sitemap.xml` (privacy and terms are left out until the owner publishes their text), `robots.txt` that disallows `/admin`, `/verify` and `/quotation-approval`, and redirects managed in the admin. See `SEO_CHECKLIST.md`.

## Testing layers

1. **Unit and integration** (`npm test`): Vitest, one throw-away PostgreSQL database per test file built *only* from `migrations/`. Server actions are executed with `next/headers` and `next/navigation` mocked. Covers money, numbering, auth and throttling, every action guard, the finance flows including concurrency, PDFs (text extraction and layout), mail, the owner CLI, the setup SQL, deployment files and environment handling.
2. **Real server over HTTP** (`npm run test:http`): `next build`, `next start`, a stand-in for Supabase Storage, and real requests: public pages in both languages, security headers, admin gate, forms with cookies, PDFs, verification and approval pages, uploads.
3. **Browser suite** (`npm run test:e2e`, Chromium via Playwright, in `tests/e2e/`): the whole finance flow (customer to stamped receipt and customer-signed quotation), every named button of the content portal, and page-load audits of the public site (English and Indonesian, six widths) and the admin portal (three widths). It exists because some defects only show in a real browser, such as a form control called `id` that made React drop the clicked submit button.

## Trade-offs

A single codebase in one language for the website, the portal and the backend, rendered on the server so content is in the HTML, with plain SQL and numbered migrations instead of an ORM so the database stays the source of truth. Pages are rendered on every request, which keeps editing instantly visible but means latency follows the database region; put Vercel and Supabase in the same region (`VERCEL_SETUP_GUIDE.md` §3). Long-form copy for the five core service pages is source-controlled (`src/content/`); everything else is editable in the admin.
